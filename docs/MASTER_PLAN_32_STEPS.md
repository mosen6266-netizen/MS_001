# 32 步完整开发路线图（权威清单）

> 版本：PLAN-1.1，2026-10-16。**步骤01文档审查已完成；尚未开始编写正式功能代码，步骤02技术原型待开始。**

## 用户确认的两级验收规则（2026-10-16，优先于旧文档中“每步必须本机实测”的条款）
- **开发步骤完成**：代码/文档已提交，必要的静态检查、GitHub Actions 云端编译和自动化测试通过，且无法在当前环境执行的真实设备/账号/多群验证均明确标记 DEFERRED。此时该步骤可记为 `done_dev` 并进入下一步，32步进度条统计的是**开发阶段完成比例**。
- **最终正式版验收**：需要本机实际 Windows 10/11、TDLib 原生库、合法自有账号真实登录/重启、真实群权限、72小时长稳、300会话容量/50群任务等证据；集中于最终阶段由用户测试。DEFERRED 不等于 PASS，任何阻断项未测/未通过都不得声明“正式发布验收通过”。
- 用户明确要求此前不中途安装测试包，不再催促本机测试；仍完成所有可进行的云端/模拟/CI验证。无真实密钥时只使用 mock、离线和 GitHub CI。
- 任何自动化测试失败都不能把开发步骤标为 `done_dev`；先修复后继续。首次本机测试发现重大架构问题时，按变更控制回溯修改对应代码。
- 更新 `state/project_state.json` 中 `completed_steps` 和 `deferred_release_acceptance`，新对话必须区分二者；32步进度到100%仅表示开发计划执行结束，不表示最终部署/验收完成。

## 强制执行协议

1. **一次只做一步**：新对话必须先读取 `docs/PROGRESS.md`、`docs/DECISIONS.md`、当前步章节和相关规格，不得凭聊天记忆跨步。
2. 每一步使用独立分支或可追溯提交，先完成验收再推进状态；禁止将失败步骤标记为 done。
3. 开始时写 `in_progress`，完成后填写：修改文件、测试命令/结果、提交 SHA、遗留问题、下步要求，并同时更新 `state/project_state.json`。
4. 必须区分 `未实现`、`代码完成待测`、`实测通过`。用户真正验收以前不宣布正式版完成。
5. 没有账户授权、必要的 Telegram 开发者凭证、Cloudflare 访问权限或 Windows 实机时，可以完成 mock 部分，但必须显式阻断依赖这些环境的验收。
6. 每步范围建议控制为 1 个可审查 Pull Request（必要时拆多个内部提交）；遇到复杂风险先写 ADR/子任务，不要一回合同时完成多个大模块。
7. 生产部署、云端授权写入、账号真实登录、任何真实群消息发送，必须经过用户明确授权；默认仅在 mock 和测试环境工作。
8. 必须遵守 Telegram API 服务条款和平台限制；不为虚假互动、未经请求的群发或绕过限流构建能力。

## 阶段概览

| 阶段 | 步骤 | 阶段目标 | 退出门槛 |
|---|---|---|---|
| I. 冻结设计与工程基础 | 01–04 | 范围、技术试验、工程骨架、持久化 | 工程可构建、文档有版本、迁移测试可运行 |
| II. 客户端与体验基础 | 05–08 | UI、状态管理、本地安全与诊断 | 无全局刷新闪屏、IPC/日志安全 |
| III. Telegram 真实客户端集成 | 09–12 | TDLib、登录、300 会话目录、群/话题管理 | 单账号真实登录验收、模拟负载记录 |
| IV. 剧本编辑与移植 | 13–16 | 角色选择、输入时间、媒体、跨电脑导入与预检 | 角色移植和全缺失提示通过 |
| V. 运行可靠性 | 17–20 | 50 任务调度、规则协调、回执、崩溃恢复 | 任务隔离、未知状态不盲目重发 |
| VI. 运行与长期维护 | 21–24 | 看板、提醒、历史、资源约束 | 高频更新/长稳性能报告 |
| VII. 授权与发布基础设施 | 25–28 | Cloudflare 隔离、安装/更新回滚 | 不影响 MS002、干净机器测试 |
| VIII. 完整回归与正式发布 | 29–32 | 回归、容量、72 小时、安全审计、签收 | 全部发布门禁通过 |

## 贯穿 32 步的非功能规范

- 所有数据库写入事务化，所有任务操作幂等且可审计；未知的消息发送结果不自动再发。
- UI 线程不可阻塞通信、读取、写入、图片处理；分页和虚拟滚动用于 300 账号、50 任务及大量历史。
- 账号凭据、手机号等不允许进入日志、导出剧本或 Git 历史；云端只保留许可证必要数据。
- Windows 10 已停止常规支持，仍可做兼容性测试，但必须向终端用户明确安全风险，不保证全平台持续可维护。
- 用户已于 2026-10-16 提供图标原素材；不得用 Telegram 官方 Logo 冒用官方客户端。
## 2026-10-16 补充：用户确认的时间顺序（最高优先级）

对每条消息严格按 `先等待 preSendDelayMs → 再显示正在输入 typingDurationMs → 然后发消息 → 平台回执 → 最后等待 postSendDelayMs`。例如等待 30 秒 + 输入 5 秒 = 35 秒后才提交发送；两者不重叠；暂停恢复保留当前阶段和剩余时间。这是 P0 验收条款，覆盖此前任何含糊描述。
