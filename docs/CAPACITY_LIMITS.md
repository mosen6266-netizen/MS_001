# Step30 容量边界与发布限制

| 对象 | CI合成范围 | 尚未验证 |
|---|---|---|
| 账号 | 300 SQLite本地账号元数据，501或301超限被拒绝（本项目上限300） | 300个真实Telegram账号在线、原生TDLib连接及保活 |
| 群 | 50个本地群权限映射与SQLite模拟任务 | 50个真实群同时发消息/管理员授权状态 |
| 角色 | 每群6个独立角色，全部300个角色映射 | 真实账号跨群权限与慢速模式 |
| 时间 | 模拟等待/正在输入、外部模拟回执、故障恢复 | 网络时延、消息成功率或官方限流 |
| 稳定性 | 72小时加速逻辑时钟、4320合成预算Tick | 72小时墙钟运行与持续OS CPU/内存监控 |
| 资源 | 短时CI实测Windows/Linux工作集、CPU、堆、线程、可用Windows句柄、SQLite大小 | 300真实连接下的资源曲线和重连率 |
| 数据安全 | SQLite持久化、备份、错误隔离、重启Review及全局停止 | 实机断电、磁盘满、Windows账户ACL、长期WAL行为 |

## 软件安全阈值（开发策略）

项目当前资源预算ResourceLimits使用CPU预警70%/严重95%；工作集500/850MiB；托管堆220/440MiB；线程80/150；句柄1200/2400（仅Windows已知计数）；定时器4/10；缓存768/1024；诊断日志384/512KiB。由两次连续不良样本触发降级，三次连续正常样本恢复，不会把无法获取的Linux句柄数据编造成零风险结果。

这些是当前的静态预算策略，并非真实运行300个在线Telegram账号的测量结论。遇到未确认的提交、群权限失效、同步失败或资源异常，默认进入人工复核，避免盲目重试。

**正式发布限制**：必须由真实签名Windows程序、官方tdjson、合法自有授权账号、真实网络/机器完成72小时墙钟长稳及安装回滚验收，才能对真实300账号/50群容量作达标声明。用户当前要求将真实实机测试放到最终版本，因此该项保持DEFERRED。
