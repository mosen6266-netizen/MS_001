## Automated verification

- Backup ledger tampering: real SQLite file remains PRAGMA integrity_check = ok yet a forged migration sha must be denied by PrepareRestore; no new restore candidate and no change to currently running app.db.
- Credential audit: git-tracked text only, high-confidence patterns for PEM private key, provider API secrets and tracked .env/PFX/key containers. CI intentionally does not scan Git history, GitHub account secrets, Cloudflare production resources, user profile data, untracked binary build outputs or real running processes. A clean scan is **not** proof that a secret has never leaked.
- Release readiness: 13 hardcoded requirements must all be VERIFIED with review identity, UTC timestamp and evidence reference; releaseAuthorized and final approval must be explicit. The repository begins with releaseAuthorized=false, all 13 DEFERRED. Even later with a complete manifest, the separate GitHub environment approval and actual signing PFX/SPKI checks are independently required.
- Existing full P0 integration tests cover no automated message retry, browser IPC allowlist, TDLib mock auth state, DPAPI checks on Windows, fail-closed local/offline license and disjoint Signal production resource identifiers.

## Release decision

**NOT RELEASE READY.** Developer-stage code CI can complete Step31 as done_dev after all new and historic tests pass, but that does **not** clear these release blockers, mark real 72h/native tests complete, issue a signed release or authorize actual Telegram messages. Final Step32 must attach real-world evidence to every readiness requirement; production environments must also require independent authorized reviewers.

No user secrets, wallets, sessions or Signal MS002 credentials have been read, migrated, exported or modified through this audit.
