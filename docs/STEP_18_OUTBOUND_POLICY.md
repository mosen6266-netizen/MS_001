# 第18步｜账号与群出站规则协调（离线策略内核）

项目：MOSEN Group Scheduler / `MS_001`。所有测试仅模拟预检后的自有账号与群。

## 已实现的契约
- `OutboundCoordinator.TryReserve(SchedulerJob,SendAuthority,DateTimeOffset)` 是**只有模拟出站许可**的函数；不会网络发送、调用TDLib、安排后台任务或创建真正的 outbox。
- 必须进入第17步 `Running/AwaitingSend` 阶段才可请求许可。严格核对冻结的 `AccountId` / `ChatId` / `TopicId`，不允许替换同名账号、改群、改话题、随意轮换账号绕过限制。
- 校验真实授权布尔值、30秒内授权时间、此次发送时重新读取的成员权限、照片/文本所需能力；没有当次可信来源事实时 fail closed。
- 单账号最多**一个未完成的许可**（所有群共享），多线程加锁防竞争。未知发送结果将账号锁为 `OUTCOME_UNKNOWN`，不自动重发；只有明确已处理且未标未知的准确令牌可以结束许可。令牌不包含凭据。
- 保守默认频率预算：账号间隔至少3秒、群级间隔至少3秒、账号滚动一分钟最多6次许可；调用方设置不能低于1秒两项间隔和不超过6次/分钟。安全额度不是Telegram官方配额，也不替代Telegram服务端实际限制。
- 群官方 `SLOWMODE_WAIT` 阻止整个受影响群所有账号；官方 `FLOOD_WAIT` 使受影响账号的**所有群**与受影响群共同等待。较短的后续等待不能缩短更长的有效截止；不通过不同账号或不同群绕过相关限制。
- 成员自身 `slow_mode_delay_seconds` 施加在固定账号×群组合，不重叠，也不能提前提交。最终出站接口必须始终服从 Telegram 实际限额与动态权限变化。

## 为什么没有接真实发送
- 第16步的桌面端 `LiveAuthorized=false` 和 `MembershipsFreshForStart=false` 保护仍保留；第18步**没有新增发送IPC**、真实网络调用、TDLib登录或出站服务。
- 该类只负责在第17步模拟作业抵达 `AwaitingSend` 时判定是否能请求模拟出站令牌。第19步将实现官方回执去重、未知结果处理与正式 outbox；后续把真实账号授权/群即时权限接线，最终才能允许官方合规实际发送。
- 这一步不声称账号频率和群慢速模式来自Telegram实时消息。目前 `SendAuthority` 是**可信事实注入接口**，没有实际官方事实供应者，真实运行必须拒绝而不是默认通过。

## 验收
- `tests/Policy/Program.cs` 包含账号在50个群同时请求时只授予一个许可、40个并发请求单账号只授予一个、授权过期/频道/关闭话题/群权限变更、官方账号洪水等待与群慢速模式、分钟频率预算、未知回执禁止重试、关闭后拒绝申请等合成情况。
- 使用GitHub Actions Windows、Linux运行；真实Win10/11与合法群、真实网络/服务端动态限流测试在最终正式版按用户要求集中完成。
- 不修改Signal MS002、现有Cloudflare生产授权系统，不写入任何真实Telegram会话或敏感数据。
