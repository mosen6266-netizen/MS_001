## 关键交互契约
- 每条消息的三个时间字段：`preSendDelayMs`（默认5000）、`typingDurationMs`（默认5000）、`postSendDelayMs`（默认0）。
- 执行是严格串行：`waiting_before → typing → submit → platform_confirm → waiting_after`；例如等30秒，再 typing5秒，约35秒时提交发消息；到达平台可能更晚；后台不偷偷省略等待、不把5秒包括在30秒内。
- 备注匹配：脚本中只有 `roleKey` + `roleLabel`，没有账号凭据；导入时比对所有必需备注，额外账号不影响；同名且无法唯一判定时人工确认。
- “开始”是预检触发点，任何缺失角色、群权限不足、媒体损坏、角色绑定冲突均阻止相应群启动，不偷偷换账号或隐藏失败。
- 账号权限变化、平台限制及发送结果未知，按群/账号安全暂停；不得因追求“正常运行”跳过 Telegram 限制。
- UI 不能伪造其他人的消息或“已读”，不能构建未经请求的陌生人群发或欺骗性多人对话流程。

## 用户故事模板与验收样例
- **US-01** 作为剧本编辑者，我能从已登录账号的备注中下拉选发言角色，避免手填造成错字；标准：与账号管理中的备注完全一致。
- **US-02** 作为剧本接收者，我登录5个账号，其中3个符合剧本需要的3个备注，即可在有权限的测试群完成预检；多余2个不阻止启动。
- **US-03** 作为剧本接收者，我缺少“客服B”账号，在点击开始时立即看到“缺少客服B”及受影响群；不可部分静默运行。
- **US-04** 作为调度者，我将一条消息设为发送前等待30秒与正在输入5秒：第30秒才触发输入，第35秒才提交发送；实际网络提交和平台送达可能更晚。
- **US-05** 作为管理员，我关闭主窗口后无后台发送；重新启动时结果未知的消息需要核查。
- **US-06** 作为长期用户，我升级安装后保留本地脚本和账号备注；若更新失败能受控回滚并保持数据库一致性。
- **US-07** 作为测试者，我能看到300记录容量、50任务并发的真实测试结果和机器配置；未测过的不能写“已通过”。
