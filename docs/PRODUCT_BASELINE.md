# MOSEN Group Scheduler V1.0 — Telegram 真实账号版正式发布主规格书

**版本：** 需求冻结基线 1.1（2026-10-16）  
**性质：** 设计方案与验收规范，不代表已开发或已通过测试  
**平台：** Windows 10/11 x64  
**产品工作名称：** MOSEN Group Scheduler（用户批准进入开发的范围所沿用的工作名称；公开发布前需要完成名称与图标合规审查）  
**原则：** 与 Signal Auto Scheduler MS002 完全隔离；优先稳定、可恢复、可审计与授权使用。

**需求优先级/不可变边界：** [需求矩阵](REQUIREMENTS_MATRIX.md)、[非目标](NON_GOALS.md)、[步骤01验收](STEP_01_ACCEPTANCE.md)。

## 0. 项目范围与边界

- 采用方案 A：Telegram 真实账号客户端技术栈（TDLib），非 Bot-only。
- 容量目标：最多登记并持久保存 300 个经本人/组织合法授权的 Telegram 账号会话；可配置 50 个独立群/话题任务同时处于运行态。
- 区分“已登录且会话有效”“在线连接中”“当前参与任务”三种状态。**300 个已授权会话 ≠ 保证 300 个持续在线客户端**；50 任务并行 ≠ 保证所有账号均能无限量同步发送。实际能力以正式压测、硬件条件和 Telegram 限制为准。
- 仅用于用户已获发言许可的群组/话题中的团队消息、公告、协同流程；不得用于虚假互动、骚扰、未经请求的推广，或绕过 Telegram 频率、权限和封禁限制。
- 任何阶段都不得修改现有 Signal MS002 或其生产 Cloudflare Worker/D1；只允许在新 MS_001 仓库中工作。

## 1. 必须满足的用户故事（P0）

1. 编辑每条剧本消息时，“发言账号”可搜索下拉选择当前已登录账号的**自定义备注**，支持键盘操作、头像/标签辨识，不再人工输入姓名。
2. 导出剧本时只携带“角色备注/角色键”、消息内容、顺序、媒体及相对发送间隔；绝不能包含 Telegram 登录会话、手机号、Telegram 用户 ID、API 凭据或本地机器密钥。
3. 在另一台电脑导入剧本，无须账号总数相等；只要本机备注集合覆盖剧本引用的所有角色，且相应账号在指定群有发送权限，即可使用。
4. 点击“开始运行”必须执行最新预检：检查缺少角色备注、同名歧义、已登录状态、目标群成员资格、话题存在、发送权限、媒体完整性、其他任务冲突与授权状态。预检失败显示可操作中文提示，不得静默跳过。
5. 同名备注：优先筛选属于当前群的账号；若仍有多个候选，必须选择具体账号并记住**本机/该群**的绑定，禁止随机选择。
6. 如运行期间账号备注更改，当前任务以启动时**冻结的实际账号绑定**为准，避免下一句突然转由其他账号发送；新任务重新预检。
7. 用户既可为不同群安排相同剧本，也可并行运行不同剧本。每个群任务可独立暂停、继续、停止。
8. 发生权限变化、限流、身份失效或网络不确定状态时，精准暂停受影响的任务/账号，不影响无关任务。
9. 默认窗口关闭=程序退出；保留短暂的有序关闭流程，任务不会变为隐藏后台继续发送。可选“最小化到托盘”，但不得默认悄悄常驻。
10. 更新、覆盖安装、软件崩溃、重新启动不能丢失账号备注、剧本、媒体引用、绑定规则、群选择、授权资料和历史记录。

## 2. 设计模块与页面

### 2.1 首页（统一视图、即时响应）
- 顶栏：软件版本、卡密有效期/剩余时长、连接状态、全局健康提示。
- 状态卡：总已登记账号数 / 授权有效数 / 当前在线数；已配置任务群 / 运行中 / 暂停 / 异常。
- 快捷设置：选择剧本 → 选择群/话题 → 查看角色匹配 → 启动预检 → 开始。
- 侧边栏固定，不随内容滚动；内侧内容单独滚动；窄屏清晰适配。

### 2.2 账号中心
- 登录流程：QR，必要时手机号验证码、邮箱代码、两步验证；遵循 TDLib 授权状态机。二维码到期自动更新但不反复创建账号。
- 数据：Telegram 稳定用户标识（仅本机内部使用）、备注、可选本机分组、头像、用户名、账号状态、上次成功连接时间、在群权限、最近错误。
- 支持重命名、批量搜索/筛选、删除本地会话、退出登录、暂停参与任务；危险操作二次确认并说明是否影响任务。
- 角色备注不被 Telegram 姓名变化覆盖；相同备注允许，但产生匹配歧义时预检阻止启动。
- 账号页面采用虚拟列表，300 项显示与搜索不创建 300 个组件的实时通信连接。

### 2.3 群组与话题中心
- 群关联使用 Telegram chat_id，话题使用 thread/topic ID；**群名称仅用于显示**，不能作为唯一键。
- 同步基本群、超级群、话题、账号成员关系及发言权限；账号不一定属于全部群。
- 支持搜索、收藏、标签、批量勾选、每页 10/20/50 可调、运行中的群显著标记。
- 群组慢速模式/管理员限制/只读频道明确提示，不尝试跳过限制。

### 2.4 剧本编辑器
- 左侧剧本目录；中间消息卡片；右侧上下文设置。新增/复制/删除/拖拽/多选/批量间隔/撤销重做/自动保存。
- 发言选择：从已登录账号备注下拉；支持搜索、近期、置顶，且显示不重复的可辨识信息。编辑时用“角色键”，不是持久绑定 Telegram ID。
- 内容：文字、emoji、图片与说明文字；可扩展视频/文件/带格式文字，具体以 TDLib 兼容能力为准。
- 文字编辑：所见即所得预览、@用户名等实体校验、换行、字符计数、链接检测、格式验证。
- 每条配置：发送账号角色、内容、附件、发送前等待、确认策略。全局设默认间隔与可选显示“正在输入”（应按真实客户端约定发状态）。
- 草稿/已发布版本分离：运行任务使用已发布剧本快照；正在编辑不会修改正在运行的队列。
- 导入导出：`.mosentgscript`（ZIP 包 + `manifest.json` + assets），包含 schemaVersion、scriptId、title、roles、steps、mediaHashes、requirements；禁止包含登录/机器凭据。
- 导入安全：文件大小和资源配额限制；ZIP bomb、路径穿越、恶意格式、媒体 MIME 检验；哈希校验、版本迁移；文件不可信时拒绝导入。

### 2.5 运行中心
- 50 个独立群/话题任务卡，显示运行状态、当前剧本步骤、下条倒计时、已完成进度、实际当前账号备注、最后错误。
- 任务状态机：草稿 → 待预检 → 就绪 → 运行中 → 等待平台 → 暂停/待核查 → 已完成/已停止/失败。
- 逐群暂停/继续/停止；全局紧急停止；终止后不在后台恢复发送。
- 失败汇总：按账号/群/错误类型筛选；可查看时间线、导出脱敏诊断日志。
- 首次发送和每次继续运行均进行必要的权限/账户状态检查；平台反馈出现异常立刻更新当前任务。

### 2.6 消息模板/设置/授权/日志/备份
- 统一管理运行通知文案、桌面提醒、运行完成提醒、卡密信息、数据备份和系统自检。
- 所有弹窗按现有习惯：确认左、取消右；确认绿、取消红；危险删除另设防误触和清楚语义。

## 3. 角色匹配算法（核心不可妥协）

定义 `roleKey`（剧本逻辑角色）与 `localAccountId`（本机账号记录主键），双层分离。剧本存的是角色别名，不存本机 ID。匹配标准：

1. 先对角色备注做可解释的匹配：原文精确匹配优先；导入前检查空白/Unicode 兼容等不规范形式，并由用户确认规范化，**不得静默将两个不同备注合并**。
2. 全局找得到匹配备注的所有已登记账号；按目标群成员和发送权限过滤。
3. 唯一候选：成功；无候选：`MISSING_ROLE`；有多个合格候选：读取此群曾确认的绑定，如果没有有效绑定则标记 `AMBIGUOUS_ROLE`，要求用户选定。
4. 同一个角色在同一任务内解析为同一实际账号；不同角色默认不得错误绑定到同一账号，除非用户显式设置角色别名合并。
5. 开始任务时生成不可变的 `RunBindingSnapshot`；随后编辑账号备注或修改剧本不影响当前正在发送的队列。
6. 单个剧本分配到 50 个群时必须逐群验证，例如 A、B、管理员这三种角色不一定同时属于 50 个群。
7. 预检报告提供：缺少角色、所需群及其缺失成员、重复备注冲突、无权限、登录过期、素材缺失，附可点击修复入口。预检失败绝不假装“启动成功”。

**例子：** 原作者 20 个账号，剧本只涉及 客服A/客服B/管理员；接收者本机仅 3 个账号，但备注齐全、目标群权限满足，即可运行；接收者即使 80 个账号，缺客服B仍不可启动。

## 4. 300 账号 / 50 群的架构策略

- `Account Registry` 持久保存最多 300 个授权会话及元数据；账号唯一键与独立 TDLib 存储目录一一对应。
- 采用 `Session Supervisor` + 分批连接/恢复 + 动态活跃工作池；不让主界面为每账号长期创建 WebSocket/轮询实例。正在参与任务的账号优先保持可用，休眠账号连接状态单独展示。
- `Group Task Actor`：每个群/话题具有独立任务状态机和队列；同一个账号参与多个群时，由 `Per-Account Send Gate` 协调，防止并发竞态。
- 每个发送请求都必须通过 `Permission Guard`、`Rate Limit Guard`、`Run Snapshot Guard`；不通过则暂停并提供原因。
- `Bounded Channels` 限制事件积压；反压/事件聚合/合并连续相同状态事件；监控接收事件延迟、内存、句柄、磁盘、任务队列长度。
- TDLib 原生接口封装在独立进程/分片宿主，单个分片崩溃可自动重建非发送性连接状态；不自动重放状态不明的消息。
- “300 个账号一次全部上线”不设为默认行为；分批启动，测量可用会话数、连接开销与资源曲线。若用户要求 300 同时在线，必须另列硬件/网络和平台可行性验收。
- 发送侧不得把账号轮换用于规避 Telegram 限流、封禁或反滥用机制；出现 FLOOD_WAIT 等限制，尊重平台等待状态。

## 5. 消息发送的可靠性：宁停勿重

1. 每条逻辑消息具有 `runId / stepId / groupId / accountId / attemptId`，在发送前写入不可变发送日志（outbox）。
2. 状态：PLANNED → CLAIMED → SUBMITTING → PLATFORM_PENDING → CONFIRMED / FAILED / UNKNOWN_REQUIRES_REVIEW。
3. 以 TDLib 的发送状态回调与实际平台消息 ID 为首要完成依据；本地按钮点击不能当作已发送成功。
4. 若“发送请求提交后”恰逢网络断线或程序崩溃，重启先核对平台状态和本地日志。仍不能确定时标记 `UNKNOWN_REQUIRES_REVIEW`，**不自动盲目重发**。
5. 明确未被平台接受且可安全重试的失败，采用有上限的延迟重试；账号权限限制、慢速模式、FLOOD_WAIT 等遵守平台反馈。
6. 完成判断基于每一步确认状态，不仅是定时器走完。
7. `STOP` 优先于所有待发送队列；一个进程不能有两个相同 run 的发送执行权。
8. 用户可在审计页面看到：计划时间、提交时间、平台反馈时间、群/话题、发送账号备注、消息 ID、结果与异常。

## 6. 客户端技术选型（建议基准）

| 层 | 推荐技术 | 决策原因 |
|---|---|---|
| 桌面壳 | C#/.NET LTS + WPF | Windows 长期支持、安装和生命周期控制清晰 |
| UI | React + TypeScript + 本地静态资源 + WebView2 | 商务暗色 SPA、导航不重载、虚拟列表与自动化 UI 测试 |
| Telegram | 官方 TDLib（固定版本的 tdjson 绑定） | 原生异步客户端通信、登录、会话管理 |
| 作业核心 | .NET 有界队列 + 独立状态机 | 可控并发、监控、取消和背压 |
| 本地数据库 | SQLite WAL（应用侧单写协调） | 事务与索引、启动恢复与迁移 |
| 密钥 | Windows DPAPI/Windows Credential Manager + TDLib 数据库密钥 | 密钥与用户会话隔离 |
| 授权云端 | Cloudflare Worker + D1，**新产品命名空间/资源** | 保留既有卡密设计理念，同时与 MS002 隔离 |
| 打包 | 自包含 Windows EXE 安装包 + 签名 + 分阶段更新 | 不手装 Python/Java/Signal CLI，升级可回滚 |

原生宿主与 UI 之间使用强类型进程内桥接或本机受保护 IPC，不将敏感接口直接暴露到局域网。若使用 loopback，仅绑定 127.0.0.1、随机令牌及来源检查，不能开放 0.0.0.0。

## 7. 数据持久化与目录隔离

建议主数据：`%LOCALAPPDATA%\MOSEN\TelegramScheduler\`

```text
TelegramScheduler/
  app.db
  sessions/<account-uuid>/tdlib-data/   # 仅本机授权会话
  media/                                # 内容寻址、去重
  backups/                              # 加密备份
  logs/                                 # 脱敏滚动日志
  temp/                                 # 自清理临时文件
  updates/                              # 暂存更新
```

表建议：`accounts`、`account_aliases`、`chats`、`chat_memberships`、`topics`、`scripts`、`script_versions`、`script_roles`、`script_steps`、`media_assets`、`group_bindings`、`runs`、`run_steps`、`outbox`、`platform_receipts`、`task_events`、`licenses`、`settings`、`migration_history`。

- 增加外键、唯一约束、数据库迁移版本、可恢复事务。
- 账户会话数据库**不得**放进普通剧本导出；全面备份包括会话时必须加密并提示恢复限制。
- 更新前完整可校验备份；更新失败自动切回旧程序和原数据；迁移需设计回滚或兼容机制，不依赖简单替换新库。
- 素材按哈希去重，引用计数删除，防止误删正在运行脚本使用的文件。
- 按天滚动日志、保留上限、历史记录分页、定期归档，禁止无限增长。

## 8. UI/UX 正式版强制标准

- 商务黑白灰暗色、圆角；绿色成功提示，红色危险提示；中文界面，不出现难懂英文错误码。
- **禁止保存/搜索/切换页面时全局闪屏**：单页应用局部数据刷新；路由常驻；异步加载加骨架；弹窗不触发整个页面重建。
- 固定左侧栏，页面内部独立滚动；可滚动选择下拉框；搜索 150–250ms debounce（配置项）。
- 账号/群/历史一律虚拟化或分页；大列表主线程不得同步读写数据库。
- UI 线程绝不等待 Telegram 网络回包；高频状态更新按 UI 帧或固定窗口合并刷新。
- 发送、保存、导入、删除、授权、退出都有幂等交互保护，重复点击不会执行两次。
- 按钮权限与状态一致：正在处理禁用重复点击；完成必须反馈；错误提示保留上下文。
- 运行页与首页分离，但首页可以显示任务总数及异常角标；运行页固定分页/筛选。
- 提供键盘导航、字体缩放、125%/150%/200% Windows DPI，布局不重叠，屏幕分辨率适配。
- 语义统一：未登录/已登录休眠/连接中/可用/运行中/受限/过期/需复核，避免“灰色表示什么”不明确。

## 9. 生命周期与异常处理

- 单实例锁：禁止双开导致并发写数据库或重复任务发送；第二次启动聚焦原窗口。
- 启动：先显示 UI → 读本地缓存 → 校验 DB → 检查授权 → 后台分批恢复账号 → 用户选择启动任务，禁止无确认自动重启未完成的发送。
- 退出：立即阻止新发送 → 标记任务停止/待核查 → 关闭 TDLib 会话宿主 → 检查 SQLite 落盘 → 退出进程树。不得残留后台进程占用端口。
- 突然断电/被结束进程：下次冷启动修复 WAL 状态，未确认发送变待复核，不偷偷继续。
- 睡眠/唤醒/电脑时间变化：使用单调时钟和持久化计划时间，醒来先预检，不补发过期消息风暴。
- 网络断线：不反复弹重复模态窗口；聚合系统状态，在连接恢复后先逐账号校验。
- 数据库损坏：只读隔离、保留损坏现场、验证最近备份、受控恢复；不直接删除数据。
- 媒体丢失、磁盘满、权限不足、杀毒隔离、WebView2 不可用、缺失 DLL、云端授权超时均有中文修复向导。
- 运行历史：已停止与已完成不自动变运行中；首次重启显示需人工核查任务但不发送。

## 10. Cloudflare 卡密与安全

- 新产品独立 `product_id`，独立 license 记录/规则或新 D1；不破坏 Signal MS002 的有效卡密。
- 支持测试/天/周/月/季/年/永久/自定义卡，设备绑定、续费叠加、过期/停用、管理员审计、TOTP 和一次性恢复码。
- 客户端显示到期、剩余有效时长、最近验证时间及离线宽限状态；离线策略有明确边界并对时间回拨做保护。
- Worker 仅处理许可元数据、设备识别的保护性摘要，不上传 Telegram 会话、消息正文或通讯录。
- 所有线上凭据通过 Cloudflare Secrets/GitHub Actions Secrets；绝不提交 `.env`、API hash、令牌、密钥文件。
- 导出/备份有显式隐私提示；删除账号时可选择“仅取消本地使用”或“向 Telegram 注销当前会话”（由用户确认）。
- 诊断日志自动屏蔽短信验证码、密码、令牌、手机号、聊天内容，未经用户许可不上传。

## 11. 自动更新与安装

- 安装包包含必要运行组件（TDLib native runtime、应用框架，及 WebView2 必要安装/固定版方案），无需手工 Python/Java/Signal CLI。
- 安装后桌面/开始菜单快捷方式、卸载入口；安装目录与用户数据分离，覆盖安装不清除数据。
- 更新从新仓库的 GitHub Releases 获取；版本清单、下载地址、签名/哈希验证；支持断点续传或安全重新下载、超时提示和备用下载链接。
- 更新过程中不得发送消息；正在运行的任务必须先停止或显式安排更新窗口。
- 安装包 Authenticode 代码签名是商业正式发布的强建议；降低但不能消除杀软误报风险。
- CI 产物包含版本清单、SHA256、SBOM、许可声明、更新日志和可审计构建编号。

## 12. 监控与诊断中心（默认本地）

- 指标：内存 RSS/工作集、句柄数、CPU、TDLib 会话数、实时连接数、队列深度、单事件处理延迟、UI 路由耗时、DB 查询 p95、磁盘用量、导入失败率、已确认/状态未知消息数。

## 14. 发布阻断清单（release blockers）

- 任何账号误绑定或发错群/话题。
- 网络异常导致同一句消息自动重复发送。
- 关闭窗口后仍有自动发送后台进程。
- 更新丢登录/备注/脚本/群绑定或授权状态。
- 导出的剧本包含登录会话、手机号、API hash 或个人隐私。
- 页面切换出现全局闪白/闪黑，保存操作阻塞 UI。
- 50 群任务中单群失败拖垮其他群；或双开进程造成重复任务。
- 运行中更改备注导致发送账号发生静默切换。
- 卡密服务更改影响现有 Signal MS002。
- 不遵守 Telegram API 规则，包括未经同意代发、伪造已读、规避限流、骚扰或垃圾信息发送。
