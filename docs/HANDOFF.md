## 执行顺序
1. 确认当前是 MS_001 而非 MS002 / MS007 / MS_Telegram_bot。
2. 读取最早未验收步骤并核查上一步交付、提交 SHA、测试原始证据与遗留问题。
3. 当前状态若为 `in_progress`，继续检查未完成项，不重新发明架构；若 `blocked`，解决阻断；若 `not_started`，用户同意后开发；若 `verified`，确认后推进下一步。
4. 单次只做当前步骤；先检查现有实现，再进行最小相关修改；先本地/CI 验证再提交代码；不能实测的项目写 `not_run`。
5. 每次 GitHub 提交后更新 `state/project_state.json`、`state/steps.json`、`docs/PROGRESS.md` 并记录真实提交 SHA 和本步测试证据。自引用 commit SHA 无法嵌入自身提交时，应记录前一提交并在下一提交更新或说明。
6. 给用户报告步骤、已交付内容、真实提交链接、通过/未通过及下一步。中断后不能后台自动工作，靠仓库恢复。

## 用户确认的两级验收规则（2026-10-16，优先于旧文档中“每步必须本机实测”的条款）
- **开发步骤完成**：代码/文档已提交，必要的静态检查、GitHub Actions 云端编译和自动化测试通过，且无法在当前环境执行的真实设备/账号/多群验证均明确标记 DEFERRED。此时该步骤可记为 `done_dev` 并进入下一步，32步进度条统计的是**开发阶段完成比例**。
- **最终正式版验收**：需要本机实际 Windows 10/11、TDLib 原生库、合法自有账号真实登录/重启、真实群权限、72小时长稳、300会话容量/50群任务等证据；集中于最终阶段由用户测试。DEFERRED 不等于 PASS，任何阻断项未测/未通过都不得声明“正式发布验收通过”。
- 用户明确要求此前不中途安装测试包，不再催促本机测试；仍完成所有可进行的云端/模拟/CI验证。无真实密钥时只使用 mock、离线和 GitHub CI。
- 任何自动化测试失败都不能把开发步骤标为 `done_dev`；先修复后继续。首次本机测试发现重大架构问题时，按变更控制回溯修改对应代码。
- 更新 `state/project_state.json` 中 `completed_steps` 和 `deferred_release_acceptance`，新对话必须区分二者；32步进度到100%仅表示开发计划执行结束，不表示最终部署/验收完成。
